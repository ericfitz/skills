# openapi plugin: Arazzo spec generation from the journeys doc

Date: 2026-08-20
Issues: #44 (arazzo skill), #43 (openapi plugin decision)
Status: approved in session; supersedes nothing

## Decision context

- #43 is resolved by this design: a **standalone `openapi` plugin** is created and
  **CATS stays in its own plugin**. CATS is a fuzzing toolkit with its own scripts,
  agents, and config; moving it would break existing installs for no current benefit.
- #44's input is the confirmed journeys doc that `itest:design` now persists to
  `docs/journeys.md` (issue #45, shipped in itest 1.1.0).
- The Arazzo Specification recommends the entry document be named `arazzo.yaml` or
  `arazzo.json`; OpenAPI recommends `openapi.yaml`/`openapi.json`. Neither standard
  defines a spec-pointer/discovery file; the closest public convention is APIs.json
  (`apis.yaml` at repo root). We honor the entry-name recommendations as defaults,
  use a machine-local pointer file operationally, and offer APIs.json for committed,
  team-visible discovery.

## Plugin structure

```
openapi/
  .claude-plugin/plugin.json      (v0.1.0, category: development)
  .codex-plugin/plugin.json       (generated by scripts/gen_codex_manifests.py)
  requirements.json               (env:check declarations; validators optional)
  scripts/
    find_specs.py                 (spec discovery + verification, JSON output)
  skills/
    init/SKILL.md
    arazzo/SKILL.md
  references/
    arazzo-authoring.md           (mapping doctrine + Arazzo 1.0 cheat sheet)
```

No coupling to the cats plugin: skills may read `.local/cats/config.yaml` as a
*hint* if it exists, but never invoke cats scripts or require the plugin.

## Pointer file

`.local/openapi/config.yaml` — machine-local, gitignored, mirroring the
`.local/cats/config.yaml` convention:

```yaml
openapi_spec: api/openapi.yaml   # path relative to repo root, must exist
arazzo_spec: arazzo.yaml         # where openapi:arazzo writes/reads
```

Additionally, `openapi:init` **offers** (never assumes) to generate a committed
`apis.yaml` at repo root in APIs.json format declaring both specs. If a committed
`apis.yaml` exists without an Arazzo entry, `openapi:arazzo` offers to add one
after emission.

## Skill: openapi:init

Bootstraps `.local/openapi/config.yaml`.

1. If the config already exists: print it and exit 0 (idempotent, like cats:init).
2. Run `scripts/find_specs.py` to discover candidates (see below). Also consult
   `.local/cats/config.yaml`'s spec path as a hint when present.
3. Present findings and let the user choose: **accept the recommended candidate,
   type a path, or cancel the skill**. Never finish without an existing, verified
   OpenAPI spec file. Arazzo spec path defaults to root `arazzo.yaml` (an existing
   discovered Arazzo doc is recorded instead).
4. Write the config, ensuring `.local/` is covered by the target repo's
   `.gitignore` (add the entry if missing, as cats:init does), then offer the
   committed `apis.yaml`.

### Discovery script: find_specs.py

- Candidate search via `rg` (fallback `grep -r` with equivalent excludes) over
  `*.yaml`, `*.yml`, `*.json` files only — never reads arbitrary files; rg respects
  `.gitignore` so vendored trees are skipped.
- Strong markers only:
  - OpenAPI: `^openapi:\s*["']?3` (YAML), `"openapi"\s*:\s*"3` (JSON),
    `^swagger:\s*["']?2\.0` / `"swagger"\s*:\s*"2\.0"` (legacy, reported as such)
  - Arazzo: `^arazzo:\s*["']?1` (YAML), `"arazzo"\s*:\s*"1` (JSON)
- Each candidate is verified:
  - If `vacuum`, `spectral`, or `redocly` is on PATH: run it and record the verdict
    and which validator ran. First one found wins; no installs.
  - Otherwise: structural parse (PyYAML/json) — OpenAPI requires top-level
    `openapi` + `info` + (`paths` or `webhooks` or `components`); Arazzo requires
    `arazzo` + `info` + `workflows`. Recorded as `validator: structural`.
- Output: JSON to stdout —
  `{"openapi": [{path, marker, valid, validator, detail}], "arazzo": [...]}`,
  sorted best-first (valid before invalid, shallower paths first). Exit 0 even when
  nothing is found; an empty result is data, not an error.
- Runs under `uv run python` per repo tooling; PyYAML is already a dependency.

## Skill: openapi:arazzo

### Preflight

- `.local/openapi/config.yaml` missing → **offer to run `/openapi:init` now** in
  this session; only stop if the user declines or init is cancelled.
- Journeys doc missing (default `docs/journeys.md`, overridable by argument) →
  **offer to run `/itest:design`**, noting it is a long, human-gated workflow; stop
  only if declined.
- Parse the journeys contract from the doc's fenced JSON block; if the block is
  absent, fall back to the prose sections and say so.

### Mapping

One Arazzo workflow per confirmed journey:

- `workflowId` from the journey `id`; `summary`/`description` from name + narrative;
  workflow-level `dependsOn` from `depends_on` edges.
- Steps: decompose the narrative into concrete calls and bind each to a real
  operation in the OpenAPI spec — `operationId` preferred, `operationPath` when the
  spec has no ids. Chain obvious data flow via `$steps.<id>.outputs.*` (created
  ids, tokens). Default `successCriteria`: `$statusCode` matching the 2xx the spec
  declares for that operation.
- Journeys that are not API-shaped (CLI or UI actors with no operation to bind) are
  flagged and skipped, never force-mapped.

### Human gate

Before writing anything, present the full mapping table — journey → proposed steps
→ operations — with unmapped steps and skipped journeys called out. The user
approves, edits, or drops entries. Nothing is emitted until they respond.

### Emission

- Write to the configured `arazzo_spec` path (default root `arazzo.yaml`).
- Header: `arazzo: 1.0.1` — baseline version with the widest tool support; moving
  to 1.1.0 later is additive. `info` from the repo; `sourceDescriptions` pointing
  at the OpenAPI spec by relative path.
- If the target exists: summarize what would change and ask before overwriting.
- Then offer the `apis.yaml` update (above).

### Validation

After emission, validate with `redocly`, `spectral`, or `vacuum` if on PATH and
report findings. Otherwise run a structural self-check — every `operationId`
resolves against the spec, every `dependsOn` names an emitted workflow, every
referenced step output exists — and state explicitly that no external validator
ran.

## requirements.json

Declares `rg` (optional, grep fallback) and the validators (`vacuum`, `spectral`,
`redocly`) as **optional**, so `env:check` reports degraded capability rather than
failure when absent.

## Testing

- `tests/test_openapi_findspecs.py` — unit tests for the script (TDD): marker
  matching per format, gitignore/vendor exclusion, structural verification accept
  and reject cases, external-validator branch behind a PATH stub, JSON shape and
  ordering, empty-result exit 0.
- `tests/test_openapi_coupling.py` — prose guards in the house style: init is
  idempotent and never finishes without a verified spec; init offers accept /
  type-a-path / cancel; arazzo documents the human gate, ask-before-overwrite, the
  `arazzo.yaml` default, and offers `/openapi:init` from preflight; arazzo
  references `docs/journeys.md` (cross-plugin consistency with itest:design);
  neither skill invokes cats scripts by path.
- Existing generic suites (`test_plugin_structure.py`, `test_codex_manifests.py`,
  env declaration tests) pick up the new plugin; marketplace entry added and Codex
  manifests regenerated.
